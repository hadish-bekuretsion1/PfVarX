0. What benchmarking is (and is not)

ActivityInputsWhat it establishes
Software testsSmall generated examples (development branch)Code behaviour and mathematics
Synthetic end-to-end verificationpfvarx fixtureTool integration, QC, eligibility, outputs, evaluation plumbing
Real-truth benchmarkingIndependently established truth + confidence regionsAgreement with that truth for the tested assay and context
CalibrationPredeclared development experimentsEmpirical settings with provenance; not done automatically
Held-out evaluationLocked, unseen truth partitionThe final performance estimate for the frozen experiment
Benchmark the same caller and workflow you use for analysis, in a separate workspace with purpose: benchmarking. Never reuse an analysis workspace. Never derive truth from PfVarX's own output. A successful pilot without independent truth is not accuracy validation.

3. Write the protocol before you look at any result

Record, in a file outside the workspace (for example ~/pfvarx-lab/records/BENCH_2026_01_protocol.md):

  1. Assay and design (wgs, targeted_no_umi, targeted_umi), input type, final output (FO002 for caller-only scoring).
  2. Variant scope (SNV, small indels), coverage range, mixture proportions to be tested.
  3. Reference FASTA, GFF and core mask with release and SHA-256.
  4. Truth provenance for every sample: how it was established, independent of PfVarX.
  5. Confident regions: source and how they were derived.
  6. Exclusion rules (QC failures, contamination) and the denominators you will report.
  7. Acceptance criteria (for example SNV sensitivity ≥ X with 95% interval lower bound ≥ Y).
  8. Partition seed and held-out fraction; who may see held-out results and when.

Whereinputs/truth/ (role truth: ./pfvarx add-input --role truth --file …)Shipped?No. Truth is never downloaded or invented.
inputs/truth/
  truth.json                      # sample composition and clone variants
  confident_regions.bed           # where truth is complete (zero-based, half-open)

truth.json (structure)

{
  "samples": {
    "PURE_A": {"clonality": "MONOCLONAL", "true_k": 1, "components": [{"clone": "cloneA", "proportion": 1.0}]},
    "PURE_B": {"clonality": "MONOCLONAL", "true_k": 1, "components": [{"clone": "cloneB", "proportion": 1.0}]},
    "MIX_AB": {"clonality": "POLYCLONAL", "true_k": 2,
               "components": [{"clone": "cloneA", "proportion": 0.7}, {"clone": "cloneB", "proportion": 0.3}]}
  },
  "clones": {
    "cloneA": [{"chrom": "Pf3D7_01_v3", "pos": 12345, "ref": "A", "alt": "G"}],
    "cloneB": []
  }
}

Positions in JSON and VCF are one-based; BED is zero-based. Mixture proportions are real DNA proportions and sum to 1; list every constituent clone. An empty clones object is valid for an all-monoclonal experiment but gives no mixture truth.

11. Check the truth before use

The evaluator is not a complete truth validator. Check yourself:

# contigs in truth exist in the reference
cut -f1 prepared/reference/parasite.fasta.fai | sort > /tmp/ref.contigs
grep -hv '^#' inputs/truth/*.truth.vcf | cut -f1 | sort -u | comm -23 - /tmp/ref.contigs     # must print nothing
# REF alleles agree with the reference (errors are reported)
for v in inputs/truth/*.truth.vcf; do ./pfvarx tool bcftools norm -f prepared/reference/parasite.fasta --check-ref e -Ou "$v" > /dev/null || echo "REF mismatch: $v"; done
# BED within contig bounds
awk 'NR==FNR{len[$1]=$2;next} !($1 in len) || $3>len[$1] || $2<0 || $2>=$3 {print "bad BED line: "$0}' prepared/reference/parasite.fasta.fai inputs/truth/confident_regions.bed
# mixture proportions sum to 1
python3 -c "import json;d=json.load(open('inputs/truth/truth.json'));[print(s,sum(c['proportion'] for c in v['components'])) for s,v in d['samples'].items()]"
# checksums for the archive
sha256sum inputs/truth/* inputs/reference/* > ~/pfvarx-lab/records/BENCH_2026_01_inputs.sha256

Run the reference checks after prepare (they read prepared/reference/parasite.fasta).

20. Metrics and how they are computed

ItemDefinition in PfVarX 0.0.0
MatchingExact (chrom, pos, ref, alt) after bcftools norm left-alignment and multiallelic decomposition
Calls scoredOnly PASS calls, with variant anchor inside the confidence BED
SensitivityTP / (TP + FN)
PrecisionTP / (TP + FP)
F1Harmonic mean of sensitivity and precision
FP per callable MbFP divided by the caller's callable span (not intersected with the confidence BED)
IntervalsWild cluster bootstrap of the linearised ratio estimator over pure samples, at layer6.benchmark_interval_level (0.95): Rademacher weights from benchmark_rademacher_min_clusters (10) clusters, Webb six-point below; every weight vector enumerated up to benchmark_bootstrap_max_vectors (9 999), otherwise that many drawn with benchmark_bootstrap_seed
Truth outside callableTruth variants outside the callability BED still count as FN: report this

Report the denominator choices when you compare with an external tool. Very small truth sets cannot establish general performance. Investigate any reference-mismatch warning from normalisation.

21. Mixtures, WSAF and K

  • WSAF calibration: regression of observed on expected within-sample allele frequency at mixture sites (slope, intercept, RMSE) and the share of sites whose interval covers the expected value, against the level the caller computed its intervals at (layer2.wsaf_interval_level, 0.95).
  • Detection by expected fraction: PASS detection rate in the bins of layer6.benchmark_wsaf_bins (0–0.1, 0.1–0.2, 0.2–0.35, 0.35–0.5, 0.5–0.999; a bin with no expected site is left out of the report, so this run shows 0.1–0.2, 0.2–0.35 and 0.5–0.999). Alleles expected at benchmark_clonal_min_expected_wsaf (0.999) or above are clonal and not scored; the calibration line needs benchmark_calibration_min_sites (3) detected sites.
  • K agreement: declared true K versus the caller's technical K.
Technical mixture K and biological COI (DA001 MOIRE) are different quantities. A summary alone does not establish mixture identifiability or clinical COI: read mixture_sites.tsv and the exclusions.

22. RTG vcfeval cross-check (optional, manual)

NeedsRTG Tools 3.13 (--rtg or development profile)Automated?No: the evaluator only reports that RTG is available

For one pure haploid truth sample:

TRUTH_SAMPLE=PF004
mkdir -p benchmarks/rtg
./pfvarx tool rtg format -o benchmarks/rtg/reference.sdf prepared/reference/parasite.fasta
./pfvarx tool bcftools norm -f prepared/reference/parasite.fasta -m -any --check-ref e -Oz \
    -o benchmarks/rtg/truth.vcf.gz "inputs/truth/${TRUTH_SAMPLE}.truth.vcf"
./pfvarx tool bcftools view -f PASS -Oz -o benchmarks/rtg/calls.vcf.gz "results/variants/samples/${TRUTH_SAMPLE}.vcf.gz"
./pfvarx tool bcftools index -t benchmarks/rtg/truth.vcf.gz
./pfvarx tool bcftools index -t benchmarks/rtg/calls.vcf.gz
./pfvarx tool rtg vcfeval --baseline benchmarks/rtg/truth.vcf.gz --calls benchmarks/rtg/calls.vcf.gz \
    --template benchmarks/rtg/reference.sdf --evaluation-regions inputs/truth/confident_regions.bed \
    --sample "$TRUTH_SAMPLE" --sample-ploidy 1 --vcf-score-field QUAL --at-score 0 --threads 2 \
    --output benchmarks/rtg/evaluation
cat benchmarks/rtg/evaluation/summary.txt

QUAL is explicit because PfVarX does not write the RTG default GQ; ploidy 1 suits a pure haploid sample; the score threshold is fixed in advance. Use a new output folder per comparison. Exact matching and haplotype-aware scoring can disagree on complex indels: report it.

23. Compare with another caller

PfVarX does not run alternative callers automatically. For a fair comparison, run the other caller through the Layer 2 adapter contract (caller.backend: external, caller.executable, caller.sha256; see SOP Appendix E / docs/caller.md) in its own benchmarking workspace, with the same reads, reference, masks, truth, confidence BED, partition and compute budget, and score both runs with benchmark-evaluate.

sha256sum /absolute/path/to/adapter
# config/config.yaml
caller:
  backend: external
  executable: /absolute/path/to/adapter
  sha256: "<64 lowercase hexadecimal characters>"
