PfVarX 0.0.0 — Operational SOP manual

Document: PFVARX-SOP-001 · Revision: 3.2 · Prepared: 12 November 2026. Audience: Linux bioinformatics researchers, developers and benchmark analysts. Authority: finalized local 0.0.0 implementation, workflow rules, parameter/policy registries and the included operating manuals. This is an operational companion, not a change to the software, calibrated settings or scientific claims. A laboratory must approve its study-specific validation protocol before routine surveillance decisions.

Read this manual in order within the relevant part. Part I is for maintainers; routine users start with Part II after the common setup. Part III uses a separate workspace. Every SOP has the same seven sections so an operator can record a formal completion.

How to use commands safely and consistently

Run commands in Bash. Stop when a command fails; inspect its error before continuing. Commands below are issued from a named workspace root containing pixi.toml, src/, config/ and workflow/. Do not execute jobs from src/ or a data directory. All paths containing $... are shell variables set below; replace any UPPERCASE sample/run identifier or /absolute/path/... resource with its real verified value. Examples are not biological data. A command block is executable only after its prerequisites have been satisfied. nano is an editor example; use your usual editor.

Set these variables once in a terminal. If the SOP bundle is moved, update SOP_HOME. Set the source path to the reviewed checkout or a fresh source-archive extraction.

export PFVARX_SOURCE=/absolute/path/to/PfVarX-source
export SOP_HOME="$PFVARX_SOURCE/docs/sop"
export LAB="$HOME/PfVarX-lab"
export DEV="$LAB/development"
export ANALYSIS="$LAB/analysis"
export BENCH="$LAB/benchmarking"
export RECORDS="$LAB/records"
BOOTSTRAP_ARGS=(--final-output FO002 --design WGS --input-type FASTQ)
mkdir -p "$LAB" "$RECORDS"
test -f "$PFVARX_SOURCE/workflow/Snakefile"
test -f "$SOP_HOME/PfVarX_SOP_Manual.md"

Keep pristine source read-only in practice. The commands create workspaces only on request. Do not copy .pixi/ between locations; install separately in each workspace. Use a full-source distribution or selected bootstrap export, not a wheel alone. ./pfvarx selects the profile environment; ./pfvarx tool TOOL runs a utility there. Plain pixi run installs the full default and is reserved here for full/development checks. Set BOOTSTRAP_ARGS before R01 for the actual profile/design/input type. For FO004 use --final-output FO004 --analyses ... with the exact requested methods; for aligned entry add --input-type BAM|CRAM. Export a new workspace for a changed capability set. Browser QA dependencies are separate. Unix utilities used include Bash, Git, find, sha256sum, gzip, awk, sed, grep, tee, df, free, nproc and a terminal editor. Confirm utilities are present. Use set -o pipefail before pipelines so an upstream failure is not hidden by tee.

Only the implemented Pixi deployment and supported input routes are documented as execution procedures. Existing VCF/joint-VCF entry, container deployment, external caller automation and proposed methods are omitted. CRAM and targeted aligned entry have implemented contracts but less extensive verification than WGS BAM; validate the actual input carefully and record the evidence. No procedure here establishes field accuracy or clinical validation by software completion alone.

Biological handling rule: use the implemented haploid dominant-allele representation; retain WSAF and uncertainty for mixtures. GT=0 at a retained low-frequency candidate can mean a reference dominant allele while an alternative allele is present. It does not make the alternative record a reference call. Missing VCF positions are not known reference genotypes. UNKNOWN marker states are not wild type. Technical DNA-mixture K, MOIRE biological COI and FWS are distinct quantities. AT-rich/low-complexity regions, homopolymers, amplification bias and uneven target coverage require stratified review. Do not apply human diploid defaults or generic low-complexity filtering automatically.

Operator record required for every SOP

In $RECORDS, keep an execution sheet with SOP ID, operator, date, workspace, source commit/version, input checksums, exact commands, exit codes, run ID, deviations, output paths, QC decision, exclusion reason and reviewer sign-off. Example header:

printf 'sop_id\toperator\tdate\tworkspace\trun_id\tstatus\tdeviation\treviewer\n' > "$RECORDS/execution-template.tsv"

This creates a blank form, not evidence that any procedure ran. Do not log tokens, passwords or the complete environment. For JSON commands keep stdout separate from stderr. pipeline returns nonzero for incomplete/failure outcomes; QC exclusion and scientific ineligibility must be reviewed independently of process completion.

PART I — Development and implementation

These procedures maintain the existing implementation. They do not instruct a researcher to replace the working caller with placeholders or a different variant caller. D01 creates the entire real directory/module tree by copying source; subsequent SOPs identify which existing files to edit, how to test a change, and when to reject it.

D01 — Initialize an isolated development checkout

1. Procedure identification

Module: repository and packaging. Workflow: development.

Purpose and scope: Create the actual source/module/workflow tree without bringing study outputs into development.

2. Prerequisites and requirements

Common setup completed; finalized source available; Git and Python 3 available. $DEV must not exist. Linux x86-64 is the supported host.

3. Detailed operational procedure

Step 1. Create the development directory tree

test ! -e "$DEV"
cp -a "$PFVARX_SOURCE" "$DEV"
cd "$DEV"
python3 scripts/package.py --check
find src/pfvarx workflow config tests -type f | sort

Step 2. Initialize local development history if this is a source extraction

git init -b main
git config user.name "YOUR_REVIEWED_COMMIT_NAME"
git config user.email "YOUR_VERIFIED_COMMIT_EMAIL"
git add .
git diff --cached --stat
git commit -m "Import verified PfVarX source"
git switch -c codex/development

4. Expected outputs

$DEV/{src/pfvarx,workflow/rules,workflow/scripts,config/templates,config/parameters,config/registry,config/geo,tests,docs,scripts} and local Git metadata. No inputs, runs or results initially.

5. Verification and quality control

Before Git initialization, the source check must report PASS and zero runtime files. Inspect staged files; raw reads, reference genomes, caches and reports must be absent.

6. Error handling and troubleshooting

Existing $DEV: stop and choose a new directory; do not copy inside it. Missing source components: re-extract the reviewed source archive. Do not copy a full analysis checkout as a substitute.

7. Completion criteria

Record source archive SHA-256 or reviewed commit, branch and clean initial tree. Continue to D02 only when the imported tree is complete.

D02 — Install the locked Pixi environment

1. Procedure identification

Module: Pixi and declared Bioconda/Conda dependencies. Workflow: development.

Purpose and scope: Install the release-supported dependency environment without altering the lockfile.

2. Prerequisites and requirements

D01 complete; Linux x86-64; Pixi available; network or cached packages; disk sufficient for both installation and separate test data. The full default environment is required for all implemented methods.

3. Detailed operational procedure

Step 1. Inspect hardware and install

cd "$DEV"
pixi --version
uname -m
nproc
free -h
df -h "$DEV" /tmp
pixi install --locked
pixi run pfvarx version

pixi run samtools --version

pixi run Rscript -e 'for (p in c("moire","dcifer","mgcv","jsonlite")) { stopifnot(requireNamespace(p, quietly=TRUE)); cat(p, as.character(packageVersion(p)), "\n") }'

4. Expected outputs

Location-specific .pixi/envs/default/ and installed tools specified by pixi.toml/pixi.lock. Save version outputs in the execution record; no environment is included in source distribution.

5. Verification and quality control

Locked installation and CLI checks must succeed. Confirm actual RAM and disk availability, not just planner estimates. Version declarations must remain consistent.

6. Error handling and troubleshooting

Outdated lock: maintainers review the dependency change and matching lock; routine users do not regenerate it to bypass an error. Disk quota: relocate a new workspace or remove only disposable test work. Never move a live installed prefix.

7. Completion criteria

Full default Pixi environment installed, essential executables/packages present, and source/lock identity recorded.

1. Procedure identification

Module: configuration/models.py, loader.py, config/. Workflow: development.

Purpose and scope: Develop validated user configuration while preserving protected scientific policy.

2. Prerequisites and requirements

D02 complete; current schema, tests/unit/test_configuration.py and template files. Change user schema only with matching validation and migration/documentation changes.

3. Detailed operational procedure

cd "$DEV"
sed -n '1,240p' src/pfvarx/configuration/models.py

Step 2. Edit schema, templates and GUI help together

The CLI (YAML templates) and the configuration GUI configure the same settings, so a setting change touches both in the same commit (see “CLI and GUI parity” in docs/architecture.md). Setting help lives only in gui/field-guide.json; regenerate the configuration guide from it.

pixi run pytest -q tests/unit/test_configuration.py tests/unit/test_cli_gui_parity.py

pixi run typecheck

Step 3. Inspect the effective parameter provenance on a test workspace

Use the isolated fixture workspace from D16; inspect its runs/<RUN_ID>/frozen_config.json. Confirm each numerical parameter retains a value and source class. Do not relabel UNCALIBRATED_PROVISIONAL as calibrated without independent experimental evidence.

4. Expected outputs

Updated schema/template/test source, and test records outside pristine source. No study configuration or empirical result is a release default.

5. Verification and quality control

Unknown keys and invalid assay combinations must be rejected by existing/new regression tests. Retain both analysis and benchmarking template validation.

6. Error handling and troubleshooting

Validation accepting an invalid combination: add a failing regression before correcting the owning model. Template/schema disagreement: reject the change. Do not permit user configuration to disable fixed gates.

7. Completion criteria

Configuration tests, lint and type checks pass; documentation and parameter source classes reflect the actual change.

D05 — Develop FASTQ preprocessing and QC

1. Procedure identification

Module: workflow/rules/l1_fastq_qc.smk, the fastp options in fastp_args (workflow/rules/common.smk) and layer1.yaml. Workflow: development.

Purpose and scope: Maintain fastp behavior without erasing AT-rich sequence or inline UMIs.

2. Prerequisites and requirements

D02; original paired reads represented by synthetic branch fixtures; existing fastp rule and layer1 parameter registry.

3. Detailed operational procedure

Step 1. Inspect branch-specific options

cd "$DEV"
cat workflow/rules/l1_fastq_qc.smk workflow/rules/common.smk
cat config/parameters/layer1.yaml

Step 2. Edit only the owning rule/parameter and exercise assay branches

nano workflow/rules/l1_fastq_qc.smk
pixi run verify wgs targeted umi --output "$LAB/verification-D05"

Step 3. Review generated fastp reports

In each new scenario workspace inspect results/qc/samples/<S>/<S>.<LANE>.fastp.json and .html. UMI extraction must precede any trimming that would remove inline molecular tags. Preserve the AT-rich low-complexity policy; poly-G handling follows the declared chemistry.

4. Expected outputs

Updated rule and per-lane fastp JSON/HTML in disposable verification workspaces. Trimmed FASTQ lives under run results/work/trimmed/ and may be deleted by Snakemake temp() semantics.

5. Verification and quality control

Compare paired retained-read counts, length distributions and adapter/quality summaries against the predeclared fixture expectations; do not require a particular retained percentage for every assay.

6. Error handling and troubleshooting

UMI structure failure after trimming: inspect extraction order. Unexpected AT-rich depletion: review any newly enabled complexity filter. Revert unqualified changes rather than relaxing QC.

7. Completion criteria

All three branches run correctly and preprocessing differences are documented with output comparisons.

D08 — Develop the custom SNP and indel caller

1. Procedure identification

Module: caller/call.py, stats.py, pairhmm.py. Workflow: development.

B12 — Review built-in summary metrics and uncertainty

1. Procedure identification

cd "$BENCH"

import csv,json
rows=list(csv.DictReader(open("benchmarks/development/per_sample_accuracy.tsv"),delimiter="\t"))
for kind in ("SNV","INDEL"):
    selected=[r for r in rows if r["status"]=="SCORED" and r["variant_type"]==kind]
    if not selected:
        print(kind,"NO SCORED SAMPLES");continue
    tp,fp,fn=[sum(int(r[k]) for r in selected) for k in ("tp","fp","fn")]
    print(kind,dict(tp=tp,fp=fp,fn=fn,sensitivity=tp/(tp+fn) if tp+fn else None,

PYCODE

Step 2. Interpret the supplied intervals correctly

Human DNA removal (optional, whole-genome sequencing only)

Reads from blood or dried blood spots carry human DNA. With reference.host_removal: true (GUI: Human DNA removal) and reference.host_fasta set to a human primary-assembly FASTA without ALT contigs, each FASTQ read pair is aligned once with bwa-mem2 to the parasite and human genomes together. Pairs whose best (primary) alignment of either mate is on the human genome are removed before duplicate marking; secondary and supplementary hits on human contigs, and human entries in SA/XA tags, are removed from the pairs kept. The BAM keeps the parasite contigs only, so calling, cohort and annotation are unchanged. Each sample's QC records host_templates_removed, templates_before_host_removal and host_fraction (gate G2.host_fraction, reported, not gated). BAM/CRAM input is used as it is. With host_removal: false (the default) reads align to the parasite genome only and host_fasta is ignored.

wgs Eligible (optional)

Targeted libraries are built from parasite-specific amplicons or probes, so human reads are a small off-target share that the on-target QC already measures. host_removal: true with a targeted design is refused when the configuration is loaded (CLI and GUI), with the message to set it to false.

Inputs Preparation runs four stages in order and stops at the first failure:

  1. Sample metadata (prepare-samples). When prepared/samples.tsv (the fixed samples_tsv setting) does not exist, it is built from the input files, with its folder: paired FASTQ names give one row per sample and lane, and library_id defaults to sample_id, so review them.     No (not created; ignored if present) continues with the sample metadata only (NOT_USED)

Supported input content

PfVarX recognises every input file by its content and structure, never by its name or extension. A file is accepted when its bytes show that it is the right kind (FASTA header lines, FASTQ records, BAM/CRAM headers, BED or GFF columns, a sample-sheet, primer or catalogue header), and refused, with an explanation, when they do not.

Folder Accepted content
inputs/reference/ FASTA sequence, BED intervals (core mask), GFF3 annotation
inputs/fastq/ FASTQ reads, plain or gzip-compressed
inputs/bam/ BAM or CRAM alignment (as configured) and its index (.bai, .csi or .crai content)
inputs/targets/ BED intervals (targets, probes) and the primer table, named by a panel in the library catalog

Two naming rules remain because tools depend on them. fastp decides from the name whether reads are compressed, so a gzip-compressed FASTQ must end in .gz and a plain one must not; otherwise fastp reads no records without an error. Reference, BED, GFF, primer, sample-sheet and catalogue files must be uncompressed, because PfVarX reads them as plain text.

When a setting in config/config.yaml names only a folder (for example core_mask_bed: inputs/reference/), PfVarX uses the one file in that folder whose content suits the setting. With no such file, or several, validation reports the problem and lists the candidates. Validation also checks the structure of each file: FASTA sequences, BED intervals within the contigs, GFF3 columns, contigs and gene/CDS features, the primer table, the catalogue columns and status, FASTQ record pairing and quality encoding, and alignment headers, sorting and read groups. The right content alone does not establish scientific suitability: check that the files match one reference release.

The Input files categories follow the saved configuration and existing input folders. After changing input type, save before returning to Input files. Folders from earlier settings can remain on disk while their tabs are hidden.

Inputs Preparation builds a missing sample sheet from the input files (a blank template for BAM/CRAM input). Fill or review it, or register a reviewed manifest, then rerun preparation. Existing sheets are preserved.

Appendix G — Assay design, library records and conditional analysis

Paired-end short-read genomic DNA is fixed. One run setting selects the processing branch: assay_design (wgs, targeted_umi or targeted_no_umi). Each design accepts FASTQ and BAM/CRAM entry (input_type). Read depth and filenames alone cannot identify a laboratory protocol, so what each library is is recorded per sample in the manifest and in the library catalog, and the pipeline checks it against the design.

Designs and their branches

Primer trimming needs primers: a panel with only probe definitions (capture) is not trimmed. On RESUME, top-level Snakemake logs advance to the next logs/snakemake.passN.log. Method-level logs can still be reused on retry. Archive them before resuming if their original contents are needed.

Transfer raw data and run preflight

After saving, open Input files to upload reads (inputs/fastq/) or BAM/CRAM files (inputs/bam/) or download them using an HTTPS link and destination filename. Trusted SHA-256 is optional. When provided, PfVarX checks it before saving. Otherwise, PfVarX records the computed checksum and marks the download unverified. Put reference files in inputs/reference/.

Register the files before running Workflow Readiness Checks → Run readiness checks. The tab runs validate, prepare, verify-prepared, and ready in that order and stops on failure.
