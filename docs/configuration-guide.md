# PfVarX configuration guide

Version 0.0.0. Open the editor with `./pfvarx configure --gui` from your study workspace. Choose settings from the actual laboratory protocol and intended output. Save the form to create input directories. When editing YAML directly, run `./pfvarx init` after saving.

The editor shows project settings from `config/config.yaml`, quality settings from `config/quality.yaml`, and compute settings from `config/compute.yaml`. Values below use YAML names. `null` means leave an optional field unset. Relative paths are resolved from the workspace.

## Project and input

| Setting | Accepted values or example | When to use it |
| --- | --- | --- |
| `schema_version` | `pfvarx.config/4` | Keep the value generated by this release. |
| `purpose` | `analysis or benchmarking` | Use analysis for study data. Use a separate benchmarking profile for independently specified truth and partitions. |
| `project_id` | `Grace_WGS_01` | Use 1–64 letters, digits, underscores or hyphens. Start with a letter or digit. |
| `input_type` | `FASTQ, BAM, CRAM` | Use FASTQ for paired .fastq or .fastq.gz reads. Use BAM or CRAM for coordinate-sorted indexed alignments, and record each file's processing_state in the sample manifest (required for targeted designs) so only the missing steps run. Lower-case fastq and bam are accepted. Bootstrap a matching input profile. |
| `final_output` | `FO001, FO002, FO003, FO004` | FO001 stops at alignment/QC and is FASTQ-only. FO002 adds per-sample calls. FO003 adds cohort integration. FO004 adds eligible downstream methods. Install the corresponding profile. |
| `samples_tsv` | `prepared/samples.tsv` | The sample metadata: one row per sample and lane, with its input files and library. Inputs Preparation builds it from the input files and creates its folder: paired FASTQ names give sample and lane IDs, and library_id defaults to sample_id, so review them. For BAM/CRAM input it writes a blank template for you to fill in. An existing file is never overwritten. Fixed path; not shown in the configuration form. |
| `study_metadata` | `No or Yes (false or true in YAML)` | Study Metadata. Yes: you supply a study table (tab-separated, with a sample_id column, for example country, latitude, longitude, collection_date, population), Input directories creates its folder, and Inputs Preparation merges it into the sample metadata, filling empty cells only and listing differences. No (default): no study metadata folder is created and the pipeline continues with the sample metadata built from the input files. DA007 needs country, latitude and longitude in decimal degrees and collection_date in YYYY-MM-DD; grouped analyses need population or the configured grouping column. |
| `study_metadata_dir` | `inputs/metadata/` | Folder for the study metadata table, used when Study Metadata is Yes; ignored when it is No. Put one study table in it. If it holds several, Inputs Preparation asks which one to merge (./pfvarx inputs-preparation --metadata-table PATH). |
| `run_policy` | `CONTINUE_INDEPENDENT or STRICT` | Use the default to let eligible independent methods continue. Use STRICT when exclusions should stop dependent execution under the strict policy. |
| `random_seed` | `20261106` | Nonnegative integer. Record and reuse it when repeating a study setup. |

## Assay

| Setting | Accepted values or example | When to use it |
| --- | --- | --- |
| `assay_design` | `wgs, targeted_umi, targeted_no_umi` | Selects the processing branch. Use wgs for direct and selective (sWGA) whole-genome libraries, targeted_no_umi for amplicon or panel libraries without UMIs, and targeted_umi when reads carry UMIs or imported BAMs are UMI consensus reads. FASTQ and BAM entry work with every design. The technique label, amplification route, panel and library protocol of each library go in the sample manifest. |
| `assay.library_catalog` | `inputs/metadata/library_catalog.yaml or null` | Required for targeted designs. A YAML file listing panels (panel_id, panel_version, targets BED, primers or probes) and library protocols (library_protocol_id, adapters, UMI read structure and consensus settings). Manifest rows name their panel and protocol by these IDs. |
| `assay.two_colour_chemistry` | `false or true` | Enable only for documented two-colour chemistry when poly-G trimming applies. |
| `assay.platform` | `ILLUMINA` | Record the real sequencing platform. This field does not install additional assay support. |

## Reference

| Setting | Accepted values or example | When to use it |
| --- | --- | --- |
| `reference.fasta` | `inputs/reference/Pf3D7.fasta` | Use the exact parasite assembly underlying the reads or existing alignment. Enter the full file path, including the filename. Relative paths start at the study workspace. If you give only a folder, PfVarX uses the one file in it whose content is a FASTA sequence; with none or several, validation asks for the full path. |
| `reference.core_mask_bed` | `inputs/reference/core_genome.bed` | The accessible core of the genome: the Core regions of Miles et al. 2016, as used by MalariaGEN, not a gene list. Variants are called and depth QC is measured only inside it. Check contig names and coordinates against the FASTA. Enter the full file path, including the filename. Relative paths start at the study workspace. If you give only a folder, PfVarX uses the one file in it whose content is BED intervals; with none or several, validation asks for the full path. |
| `reference.host_removal` | `False or True` | Human DNA removal, optional and eligible only for the wgs design (not available for targeted_no_umi or targeted_umi). True: each FASTQ read pair is aligned once to the parasite and human genomes together, and pairs whose best alignment is on the human genome are removed before duplicate marking and counted (host_fraction in sample QC). False (default): reads are aligned to the parasite genome only. True needs the Human genome reference and a bwa-mem2 index of the combined reference that you build on a machine with enough memory (./pfvarx prepare lists the steps). Not applied to BAM/CRAM input. |
| `reference.host_fasta` | `inputs/reference/GRCh38_no_alt.fasta` | Human genome reference (FASTA), used when Human DNA removal is True (wgs only); ignored when it is False. Use a primary-assembly FASTA without ALT contigs. Enter the full file path, including the filename. Relative paths start at the study workspace. |
| `reference.release_label` | `PlasmoDB 68; Pf3D7 - release unknown; Custom reference - study version 1; Reference source and release unknown` | Record the exact release of your FASTA and GFF, checked against its download record or accompanying README. Use PlasmoDB 68 only if you verified that release. The template placeholder SET_REFERENCE_RELEASE must be replaced before input directories are created. |
| `reference.gff` | `inputs/reference/Pf3D7.gff or null` | Use the GFF from the same release as the FASTA. It is needed for explicit FO004 and enables annotation and marker outcomes in automatic FO004. If you give only a folder, PfVarX uses the one file in it whose content is a GFF3 annotation; with none or several, validation asks for the full path. Enter the full file path, including the filename. Relative paths start at the study workspace. |
| `reference.snpeff_genome_id` | `null or Pf3D7_study` | Leave unset to derive the ID from the release label (other characters become underscores, for example pfvarx_Pf3D7_release_unknown). Set a reviewed identifier for the reference-matched SnpEff database when needed, using letters, digits, dots, underscores and hyphens only. |

## Downstream analyses and caller

| Setting | Accepted values or example | When to use it |
| --- | --- | --- |
| `analyses.selection` | `explicit or auto` | Explicit runs selected methods. Auto is for FO004 and selects design-compatible candidates subject to QC and evidence gates. |
| `analyses.requested` | `[] or [DA001, DA003]` | Use an empty list for auto or FO001–FO003. DA001 is optional for explicit selection and runs internally when another selected analysis needs it. For explicit selection, add other installed methods as needed. DA001 COI, DA002 markers, DA003 diversity, DA004 relatedness, DA005 structure, DA006 phylogeny, DA007 spatial/temporal. |
| `analyses.scales` | `{} or {"DA003":["POPULATION"]}` | Use {} for defaults or auto. For explicit selection specify only requested IDs and supported scales from the registry. |
| `analyses.population_column` | `null or population` | Use the sample TSV column containing actual population assignments for group analyses. |
| `analyses.resistance_catalog` | `null or inputs/metadata/verified_catalog.tsv` | Use a reference-matched, independently verified catalogue for real marker outcomes. Null selects the shipped catalogue, whose draft status blocks real marker analysis. If you give only a folder, PfVarX uses the one file in it whose content is a marker catalogue; with none or several, validation asks for the full path. |
| `analyses.spatial_outcome_source` | `null or DA002` | For explicit DA007 choose DA002 and provide valid geographic and collection-date metadata. Auto resolves the source. |
| `caller.backend` | `native or external` | Choose native for the bundled caller. External requires a qualified executable adapter implementing the Layer 2 artifact contract. |
| `caller.executable` | `null or /absolute/path/to/adapter` | Required only for external. Use an absolute executable path. |
| `caller.sha256` | `null or 64 lowercase hexadecimal characters` | Required for external. Compute it with sha256sum on the exact adapter executable. |
| `retention.intermediates` | `successful or keep` | Successful allows cleanup after a successful run. Keep retains intermediates for troubleshooting. |

## Compute

| Setting | Accepted values or example | When to use it |
| --- | --- | --- |
| `compute.schema_version` | `pfvarx.compute/2` | Keep the generated version. |
| `compute.executor` | `local, hpc, server, cloud` | Local PC, single allocated HPC node, Linux server or cloud VM. The same single-host executor is used in each case. |
| `compute.max_cores` | `4` | Total CPU budget, integer at least 1. Match the assigned cores. |
| `compute.max_mem_mb` | `6500` | Total scheduling memory in MiB, at least 512. Leave room for the OS. |
| `compute.max_jobs` | `1` | Maximum concurrent jobs, at least 1. Keep 1 for a small PC. |
| `compute.tmp_disk_mb` | `20000` | Temporary disk budget in MiB, at least 256. Allow room for actual study size. |
| `compute.tmp_dir` | `null, /local/scratch` | Absolute directory for temporary files of each job, such as node-local scratch on HPC. Java tools (Picard, fgbio) and Snakemake use it. Leave null to use the system temporary directory. |
| `compute.per_job.max_threads` | `4` | At least 1 and no greater than max_cores. |
| `compute.per_job.max_mem_mb` | `6500` | At least 256 and no greater than max_mem_mb. Raise only when your allocation can fit the requested jobs. |
| `compute.per_job.max_runtime_min` | `720` | Positive minutes for planning and rule resource requests. Set the actual HPC wall time separately. |
| `compute.max_retries` | `2` | Integer 0–2. Use 0 to disable rule retries. |
| `compute.retry_memory_factor` | `1.5` | Range 1.0–2.0. Scales retry resource requests within the configured ceiling. |
| `compute.log_level` | `DEBUG, INFO, WARNING, ERROR` | Keep INFO for routine use. Tool logs have their own detail levels. |
| `compute.keep_attempt_logs` | `true` | Keep the template default. Review actual log retention and archive method logs before a retry when needed. |
| `compute.slurm_partition` | `null` | Use null for the supported modes. Set a partition in sbatch if needed. The legacy slurm executor is rejected. |

## Worked examples

Use these starting points with your own paths and laboratory protocol.

### Direct WGS paired FASTQ on a small PC

Bootstrap with --final-output FO002 with the default FASTQ/WGS choices. In the form choose FASTQ, FO002, assay design wgs and Local; record amplification_route DIRECT (or SWGA) per library in the sample manifest. Set the matching FASTA and core BED. For an 8 GB PC, start with 6500 MiB total and per job, one job, and a thread count that fits your CPU.

### Existing indexed alignment

Bootstrap with `--final-output FO002 --input-type BAM` or `--input-type CRAM`. Choose FO002. Register the alignment and index using the sample manifest, with its processing_state (wgs: aligned or duplicates_marked; targeted_no_umi: aligned or primers_trimmed; targeted_umi: aligned, consensus or consensus_primers_trimmed) so only the missing steps run. Use the same reference assembly used to align or encode it.

### Targeted UMI sequencing

Bootstrap with `--final-output FO002 --design targeted_umi`. Choose FASTQ, FO002 and assay design targeted_umi, and point `assay.library_catalog` at the library catalog. In the catalog, define the panel (targets and primers) and the library protocol with both actual mate read structures. In the sample manifest, give each row its panel_id, panel_version and library_protocol_id; the optional technique label TBS_UMI or AMPLICON must match the design.

### Automatic downstream analysis

Bootstrap with `--final-output FO004 --auto-analyses` and the actual design. Select FO004 and automatic analysis selection. Leave requested and scales empty. Supply matched annotation and an eligible catalogue for marker analysis. Add actual population, date and geography metadata where required. Review terminal reasons for excluded analyses.

### After saving

```bash
./pfvarx validate
./pfvarx prepare
./pfvarx verify-prepared
./pfvarx ready
./pfvarx dry-run
```

Register inputs before validation. Inspect each result before proceeding to `./pfvarx pipeline --mode NEW`.

## Transfer raw data and run preflight

After saving, open **Input files** to upload reads (`inputs/fastq/`) or BAM/CRAM files (`inputs/bam/`), or download
them using an HTTPS link and a destination filename. A trusted SHA-256 is
optional. When provided, PfVarX checks it before saving. Otherwise, PfVarX
records the computed checksum and marks the download unverified. Put reference
files in `inputs/reference/`. Register your reads or BAM/CRAM files before running
**Workflow Readiness Checks → Run readiness checks**. The tab runs `validate`, `prepare`,
`verify-prepared`, and `ready` in that order and stops on failure.
