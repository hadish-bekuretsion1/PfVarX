# Sample analysis

This guide operates the implemented PfVarX pipeline on study samples. Keep truth
resources and calibration experiments in a separate benchmarking workspace. Read
[scientific status](../status.md) before interpreting outputs.

## 1. Bootstrap a new analysis-specific workspace

From the reviewed source checkout (or the root files of a sparse Git clone):

```bash
python3 bootstrap.py --profile sample --workspace ../pfvarx-analysis
cd ../pfvarx-analysis
```

Use `--profile cohort` for FO003, or `--profile downstream --analyses DA003 DA001`
for selected FO004 methods. Choose this before installation; a sample workspace cannot
be promoted above its installed capabilities by editing a YAML file. Add the actual
`--design TARGETED_NON_UMI|TARGETED_UMI` and `--input-type BAM|CRAM` at bootstrap when
appropriate. A new destination is required; original scientific inputs can be shared
read-only by absolute path. The installed `./pfvarx` launcher selects its locked environment.

Bootstrap creates three editable files: `config/config.yaml`, `quality.yaml`,
`compute.yaml`; capability metadata in `config/installation.json`; input folders are created after GUI save or after editing YAML and running `./pfvarx init`. Edit actual assay,
UMI structure, resources, outputs and compute limits before analysis. No samples or
references are fabricated. Full-source/development users may still install the full
default environment and use `config-init`/`init` explicitly.

See [orchestration](../orchestration.md) for the complete command contracts.

## 2. Select the assay and final output

Use exactly one final-output mode per run:

| Mode | Runs through | Use |
|---|---|---|
| FO001 | Read processing and QC | Review alignments before calling |
| FO002 | Per-sample calling | Recommended first real-data pilot |
| FO003 | Cohort integration | Build a variant-only cohort and evidence matrix |
| FO004 | Annotation and requested downstream methods | Eligible scientific analyses |

Example WGS configuration (edit these fields in `config/config.yaml`; retain the
other schema fields generated by `config-init`):

```yaml
purpose: analysis
project_id: STUDY_A
final_output: FO002
input_type: FASTQ
assay:
  design: WGS
  amplification_route: DIRECT
  read_structure: null
  targets_bed: null
  primers_tsv: null
  two_colour_chemistry: false
  platform: ILLUMINA
reference:
  fasta: inputs/reference/Pf3D7.fasta
  gff: null
  core_mask_bed: inputs/reference/core_genome.bed
  release_label: YOUR_EXACT_REFERENCE_RELEASE
  snpeff_genome_id: null
analyses:
  requested: []
  scales: {}
  population_column: null
  resistance_catalog: null
  spatial_outcome_source: null
```

Use `amplification_route: SWGA` only if selective whole-genome amplification was
actually performed. For two-colour chemistry, set `two_colour_chemistry: true` when
appropriate for the sequencer. Do not infer amplification or UMI design from FASTQ
filenames. Configure a pilot first, then expand to the cohort after reviewing QC.

### Targeted designs

| Field | Without UMI | With UMI |
|---|---|---|
| `assay.design` | `TARGETED_NON_UMI` | `TARGETED_UMI` |
| `assay.amplification_route` | `AMPLICON` | `AMPLICON` |
| `assay.targets_bed` | Matching target BED | Matching target BED |
| `assay.primers_tsv` | Matching primer definitions | Matching primer definitions |
| `assay.read_structure` | `null` | Two fgbio read structures, e.g. `8M+T 8M+T`. A fixed final template segment (`8M143T`) is accepted and run as `8M+T`, because adapter trimming shortens reads |

Target BED coordinates are zero-based, half-open. Primer TSV uses the fgbio TrimPrimers header `chrom`, `left_start`, `left_end`,
`right_start`, `right_end`, with one-based inclusive coordinates satisfying
`1 <= left_start <= left_end < right_start <= right_end <= contig_length`. UMI structures must
match the sequenced reads, not trimmed consensus reads. WGS marks duplicates;
targeted branches clip primers; UMI processing extracts tags, groups molecules,
calls/filters consensus, realigns, and clips primers before calling.

## 3. Supply the reference and register samples

After editing the assay fields:

```bash
./pfvarx init
```

`init` creates only the input directories needed for the chosen purpose/design and
an empty `inputs/metadata/samples.tsv` header. It does not fabricate data, references,
truth, results or masks. Populate the input paths from your own verified resources.

| Resource | Requirements |
|---|---|
| FASTA | Exact parasite assembly with stable contig IDs and lengths |
| Core BED | The accessible core of that assembly: the Core regions of Miles et al. 2016, as used by MalariaGEN, in zero-based BED. A gene or feature BED is not a core mask; validation warns (`CORE_MASK_SUSPECT`) when the file looks like one |
| GFF3 | Required for explicit FO004 and for annotation/marker outcomes in automatic FO004 |
| Targets / primers | Required for targeted assays, matched to the reference |

Reference and input paths may be absolute or relative to the workspace root. Files are recognised by their content, not their names: any name works as long as the content is right (a gzip-compressed FASTQ must still end in `.gz`, which fastp requires). If a setting names only a folder, PfVarX uses the one file in it with suitable content; see [supported input content](../configuration.md#supported-input-content). Original
inputs are read only; derived indexes are created under `prepared/`, not beside the
original FASTA. An unset GFF is valid for FO001–FO003. If a GFF path is configured,
validation expects that file even when annotation is not requested. Record the actual
reference release; do not leave the template placeholder.

Do not use a whole-chromosome or simulated mask as a validated core definition.
Deliberate simulated masks belong only in labelled software experiments. Keep
reference, mask, primer and catalogue checksums alongside the study protocol.

The sample sheet is tab-delimited, one row per sample/lane, with these columns:

```text
sample_id lane fastq_1 fastq_2 bam vcf library_id flowcell_type population country latitude longitude collection_date
```

The line above lists column names for readability; the generated template contains
actual tabs. Keep unused fields empty. Example FASTQ rows (replace paths and preserve
tab separators):

```text
sample_id	lane	fastq_1	fastq_2	bam	vcf	library_id	flowcell_type	population	country	latitude	longitude	collection_date
S01	L001	inputs/fastq/S01_R1.fastq.gz	inputs/fastq/S01_R2.fastq.gz			LIB01	unpatterned	GROUP_A				
S02	L001	inputs/fastq/S02_R1.fastq.gz	inputs/fastq/S02_R2.fastq.gz			LIB02	patterned	GROUP_B				
```

The example block contains tab-separated columns; using the generated template avoids
separator and column-order mistakes. `sample_id`, `lane`, and `library_id` are required. Sample/lane pairs
must be unique. IDs accept letters, digits, `_` and `-` within the documented schema
lengths. Multiple lanes for one sample use the same sample ID and appropriate library
IDs. Declare `patterned` or `unpatterned` from real instrument metadata when known;
this selects Picard's optical-distance setting. Duplicates are marked once per WGS sample,
so all lanes of one sample must share a flow-cell type; validation rejects a sample that
mixes them (register those lanes as separate samples). Do not invent population/location data.

### BAM/CRAM entry

Set `input_type: BAM` or `CRAM`; fill `bam` rather than FASTQ columns. Inputs need valid
coordinate sorting, matching reference dictionary/MD5, index and sample read groups.
The sample ID must match `@RG SM`. WGS duplicate marking is repeated if no marking
program is recorded. Targeted entry requires evidence of primer clipping in `@PG`.
CRAM handling is implemented but has less end-to-end validation than WGS BAM.
VCF entry is not a validated operating route in this release; start from FASTQ or
validated alignments for a benchmark-ready workflow.

## 4. Set the compute envelope

Review `config/compute.yaml` against the local machine. Keep per-job threads/memory
within total limits; leave enough memory for the operating system. The default is four
cores, one job at a time and 6,500 MiB. If physical RAM is below that, lower both total and
per-job memory or use a larger machine. Jobs exceeding the declared envelope are blocked in
planning. Every `executor` value runs the same single-host executor; on HPC, submit the run
inside one node allocation (see the [deployment guide](../deployment.md)). Temporary-disk
requirements are heuristic estimates; check actual free space too. Set `tmp_dir` to an
absolute directory (for example node-local scratch) to send Snakemake, Picard and fgbio
temporary files there instead of the system temporary directory.

The custom caller uses one worker per sample and can be much slower on a full genome
than on synthetic fixtures. It performs read evidence extraction, fitting, indel
rescoring and bootstrap mixture selection. Runtime estimates are UNKNOWN unless a
compatible measured profile exists. Resource requests guide scheduling; they are not
OS-enforced memory or wall-time limits. Do not alter scientific thresholds to make a
slow or poor-quality sample pass.

## 5. Validate, prepare and inspect the plan

```bash
./pfvarx check-layout
./pfvarx validate
./pfvarx prepare --dry-run
./pfvarx prepare
./pfvarx prepare --dry-run
./pfvarx ready
./pfvarx dry-run
```

Expected outcomes:

1. `check-layout` reports required directories/files and misplaced runtime paths.
2. `validate` writes `metadata/validation_report.json`, checks complete FASTQ mate
   structure/counts/names, samples quality encoding, and validates configured resources.
   Its `summary` names each problem or warning, why it failed, why the input matters and
   numbered steps that fix it.
3. `prepare --dry-run` lists missing/stale indexes without performing preparation.
4. `prepare` derives the combined/parasite FASTAs and required indexes under `prepared/`.
5. A second preparation plan has no actions if the inputs are unchanged.
6. `verify-prepared` must PASS: derived hashes, FASTA/FAI/dictionary compatibility
   and current input validation are mandatory. Then `ready` must report `ready: true`; review resources and deferred gates.
7. `dry-run` checks the Snakemake DAG up to runtime checkpoints and creates no `runs/`
   or `results` directory. Later QC and eligibility outcomes are not known yet.

A partial input-validation result can isolate individual failing samples under the
continue-independent policy; global reference/configuration errors must be resolved.
Archive the validation report and input checksums before a study run.

## 6. Execute and verify

```bash
./pfvarx pipeline
./pfvarx status
./pfvarx run-verify --run-id YOUR_RECORDED_RUN_ID
```

Record the run ID returned by `pipeline`. A successful process result does not imply
that every sample or requested scientific method was eligible. Check the run's status,
per-sample QC, diagnostics and terminal manifests. Do not relax gates to obtain a
particular biological result.

## 7. Find and interpret outputs

Runtime directories are created on demand. The distribution ships none of this data:

```text
inputs/                       user-supplied read/reference/metadata resources
prepared/                     derived reference/indexes
metadata/                     input-validation records
runs/<RUN_ID>/
  frozen/                     copied run-defining configuration and software
  frozen_config.json
  frozen_plan.json
  snapshot.json
  status.json
  logs/                       workflow/tool logs and structured diagnostics
  benchmarks/                 measured job resources, when recorded
  results/
results -> runs/<RUN_ID>/results
```

| Result path under `results/` | Meaning |
|---|---|
| `alignments/<sample>.bam` and `.bai` | Processed alignment |
| `qc/samples/<sample>/qc_decision.json` | Layer 1 decisions, thresholds and permissions |
| `qc/samples/<sample>/<sample>.caller_qc.json` | Caller depth, callability, fit and mixture evidence |
| `variants/samples/<sample>.vcf.gz` and `.tbi` | Variant-only SNP/small-indel records, including non-PASS statuses |
| `variants/samples/<sample>.evidence.tsv` | Counts, uncertainty and caller status per candidate |
| `variants/samples/<sample>.callable.bed` | Caller-defined usable intervals |
| `variants/samples/<sample>.focal_loss.bed` | Focal coverage losses |
| `cohort/cohort_status.json` | Whether a cohort was formed, its samples, and blocked samples with reasons |
| `cohort/cohort.vcf.gz` | FO003/FO004 variant-only cohort merge |
| `cohort/evidence_matrix.tsv.gz` | Site-forced per-sample evidence; missing is not imputed reference |
| `cohort/sites.tsv`, `cohort/missingness.tsv` | Cohort sites and missingness summary |
| `annotation/cohort.ann.vcf.gz`, `annotation_qc.json` | FO004 SnpEff consequences and annotation checks |
| `eligibility/` | Per-sample/cohort scientific eligibility decisions |
| `downstream/DAxxx/status_manifest.json` | Requested method's terminal state, denominators, exclusions and caveats |
| `downstream/DA001/clonality.tsv` | Clonality, COI median and interval, Fws (COI count and Fws only with ≥ 10 samples) |
| `downstream/DA002/marker_calls.tsv`, `prevalence.tsv` | Marker states and prevalence with intervals and the WHO kelch13 flag |
| `downstream/DA003/population_diversity.tsv` | Diversity per group with bootstrap intervals |
| `downstream/DA004/pairwise_relatedness.tsv` | Relatedness per pair: method, markers, status and label |
| `downstream/DA005/pca.tsv`, `fst.tsv` | PCA coordinates and Hudson FST |
| `downstream/DA006/tree.treefile` | Maximum-likelihood tree (with `tree.contree`, `tree.iqtree`) |
| `downstream/DA007/country_month_summary.tsv` | Prevalence by place and month; GAM fit when supported |
| `report/pfvarx_dashboard.html` | Offline report; open after the run finalizes |
| `report/dashboard_data.json` | Report data backing the HTML |
| `report/clonality_report.txt`, `.tsv` | Per sample: monoclonal, or polyclonal with the number of clones and each clone's share of the parasite DNA, for example "Sample Y is polyclonal with 3 clones: Clone 1: 50.0%, Clone 2: 30.0%, Clone 3: 20.0%" |
| `qc/centralized_quality_matrix.json` | Aggregated quality records |

Count accepted variants by `FILTER=PASS` / caller `PST=PASS`, not by total VCF rows.
Absent positions in a variant-only VCF are not reference calls. Caller technical K is
not biological COI. Unknown/uncallable resistance markers are not wild type. Separate
processing status, QC verdict and scientific eligibility. Uncalibrated results remain
labelled as such; software completion does not establish accuracy.

The dashboard supports eight sections, tables, drill-downs and CSV/XLSX/PNG exports,
plus browser print-to-PDF. View filters do not recompute scientific estimators. Generate
the final report after completion. In-progress views reflect available final artifacts
at generation time; they are not a live scheduler feed. See the [reporting manual](../reporting/README.md).

## 8. Request FO004 analyses

For FO004, bootstrap a matching downstream profile with the intended `--analyses`
before configuring it. Supply the exact matching GFF and select only installed analyses:

```yaml
final_output: FO004
reference:
  # retain the other reference keys
  gff: inputs/reference/Pf3D7.gff
analyses:
  requested: [DA003, DA001, DA005, DA006]
  scales:
    DA003: [POPULATION]
    DA005: [BETWEEN_POPULATIONS]
  population_column: population
  resistance_catalog: null
  spatial_outcome_source: null
```

That is an edit fragment, not a replacement for the entire generated configuration.

| ID | Implemented method / requirements |
|---|---|
| DA001 | MOIRE clonality with ≥ 10 informative samples; smaller cohorts take the call from the caller's mixture test (`basis` column) with no COI count or Fws; caller technical K otherwise shown only as context |
| DA002 | Codon-level resistance markers; independently verified matching catalogue required |
| DA003 | Within-host FWS and population diversity; group sizes/callability apply |
| DA004 | hmmIBD / Dcifer relatedness; DA001 and pair eligibility apply. WGS pairs need 200 informative markers; targeted pairs need 20, and pairs below 200 are `ESTIMATED_LOW_PRECISION` without a relatedness label |
| DA005 | Haploid PCA and Hudson FST; WGS, declared populations and eligible samples |
| DA006 | IQ-TREE phylogenetics; WGS, at least four eligible monoclonal samples and sufficient sites |
| DA007 | Spatial/temporal summaries; declared source outcome and country/date/coordinate metadata |

DA001 is inserted as an internal prerequisite where needed. DA006 rechecks actual
alignment informativeness and can legitimately skip after preliminary eligibility.
For DA007, set `spatial_outcome_source` to the appropriate implemented source (for
example DA002); a verified catalogue is then required for real resistance outcomes.
The shipped draft catalogue intentionally blocks real DA002 execution.

Terminal states include COMPLETED, COMPLETED_WITH_EXCLUSIONS, SKIPPED_INELIGIBLE,
BLOCKED_MISSING_PREREQUISITE and FAILED_EXECUTION. A skipped tree is not a placeholder
result; no tree is produced when requirements are unmet. If no sample passes QC into the
cohort, the run still completes: `cohort/cohort_status.json` reports
`SKIPPED_NO_ELIGIBLE_SAMPLES`, no cohort or annotation files are written, and every
requested analysis ends as SKIPPED_INELIGIBLE with `NO_ELIGIBLE_SAMPLES` and `NO_COHORT`.
Threshold values and their sources are listed in [thresholds](../thresholds.md).

## 9. Resume, extend and troubleshoot

```bash
./pfvarx pipeline --mode RESUME --run-id YOUR_RECORDED_RUN_ID
./pfvarx pipeline --mode EXTEND --run-id PREVIOUS_RUN_ID
./pfvarx report --run-id YOUR_RECORDED_RUN_ID
```

RESUME requires unchanged effective configuration and recorded software/configuration
hashes. EXTEND creates a new run and can reuse per-sample artifacts when its reuse key
matches. Preserve old sample IDs and raw inputs. Use NEW if reads, masks, primers,
reference, scientific policy or preprocessing meaning change; not every external data
file is included in the current reuse key. `run-verify` verifies recorded frozen files,
not the scientific identity of every external input. Maintain your own input manifest.

For failures, inspect `status.json`, `logs/snakemake.pass*.log`, per-tool logs and
`logs/events.jsonl`. Distinguish malformed inputs, tool failures, QC exclusions and
scientific ineligibility. Readiness can fail because memory/disk requests exceed the
machine. The caller may remain CPU-active for a long time without intermediate log
messages; there is no reliable percentage-complete estimate. Do not silently change
parameters or restart a still-running job. To regenerate a final dashboard, use `report`;
this does not rerun calling or downstream methods, and the dashboard keeps the pipeline
version recorded when the run was made.

## 10. Registration, full orchestration and retention

Use `./pfvarx discover-inputs --directory DIR` to generate a review-required candidate
sheet, then `register-inputs --manifest FILE --mode reference|link`. Imported relative
paths resolve from that manifest directory. Registration does not copy reads; existing
populated registries are not overwritten. Input/quality observations and effective
configuration/parameter summaries are generated in metadata by validation.

After configuring and registering real inputs, `./pfvarx orchestrate` performs
initialize → validate → prepare → verify → preflight → execute/report. Use
`--through validate|prepare|verify` to stop early. Explicit pipeline modes remain.

`retention.intermediates: successful` is the default; `keep` retains temporary files
for debugging. `./pfvarx cleanup --run-id ID` previews eligible completed-run work files;
`--apply` authorizes those deletions. Failed runs, original inputs/references, final
results, QC, logs and frozen records are retained. See the orchestration guide for
safety boundaries. BAM/CRAM preparation skips unused BWA indexes.

Actual reference-tool stdout/stderr is recorded under `metadata/preparation_logs/`
for each executed indexing/dictionary action. Inspect these logs when preparation fails;
failed/empty artifacts are not accepted as a verified preparation.

See the [configuration editor and input procedure](../configuration.md) and the
[sequencing and downstream eligibility matrix](../sequencing.md).
