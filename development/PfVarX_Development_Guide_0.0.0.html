0. Branch and release model

BranchHoldsWho uses it
developEverything: analysis software, tests/, .github/workflows/ci.yaml, development/, CLAUDE.md, docs/testing.md, the maintainer scriptsDevelopers. All work starts here, on a feature branch merged into develop by pull request.
mainThe same files as develop: it is brought level by a pull request from develop once a change there is tested (section 24). Release tags (v0.0.0) point at main.Users
Since 27 November 2026 (pull requests #55 and #58) main mirrors develop. What users receive is still the analysis software only: the release archive is built with scripts/package.py, which leaves out development/ and CLAUDE.md (section 22); never publish a plain git archive of main.

14. Experiment in a test workspace

Never experiment in the source tree. Make a throw-away workspace from your working copy:

python3 bootstrap.py --profile development --workspace ~/pfvarx-lab/try-1
cd ~/pfvarx-lab/try-1
./pfvarx fixture --design wgs --n-mono 6 --n-poly 3 --depth 40 --seed 7     # options: --low-depth-sample, --variant-scale N
nano config/config.yaml        # release_label: SYNTHETIC_SOFTWARE_FIXTURE; final_output; analyses
./pfvarx validate && ./pfvarx prepare && ./pfvarx ready
./pfvarx dry-run               # plan only
./pfvarx pipeline

To try a parameter value, change it in the workspace copy of config/parameters/layerN.yaml, run with --mode NEW, and compare qc_decision.json, VCF PASS counts and the dashboard. Measure accuracy with a benchmarking workspace (see the Benchmarking guide) and resources with ./pfvarx benchmark-resources --run-id RUN_ID.

Fault injection (tests only): PFVARX_FAULT_INJECT=pfvarx_call:PF002 ./pfvarx pipeline makes that sample's call job fail with exit 70, to check that the other samples continue. Never leave it set.

16. Add or change a setting

  1. Model: src/pfvarx/configuration/models.py.
  2. Help text (single source): src/pfvarx/configuration/gui/field-guide.json.
  3. Templates: config/templates/analysis.yaml, benchmarking.yaml (or quality.yaml/compute.yaml).
  4. GUI: gui/index.html, gui/app.js; shared behaviour in Python (configuration/web.py), never only in JavaScript.
  5. Regenerate the guide and check parity:
pixi run python scripts/configuration_guide.py
pixi run pytest -q tests/unit/test_cli_gui_parity.py tests/unit/test_configuration.py tests/unit/test_configuration_gui.py

A schema change also needs configuration/migrate.py and documentation of the migration (./pfvarx config-migrate).

17. Change a parameter or a QC gate

  • Parameter: edit config/parameters/layerN.yaml with its source class and a note; read it with frozen_param; list it in docs/thresholds.md; add a value to legacy_parameters.yaml if older frozen runs must keep working.
  • QC gate: edit config/registry/qc_policy_pfvarx_qc_v1.yaml (fields: gate stage metric unit direction fail warn threshold_source reference designs mandatory warning_permitted_for) and bump its version (now 1.3.0).
pixi run pytest -q tests/unit/test_no_hardcoded_parameters.py tests/unit/test_quality_eligibility.py tests/unit/test_cohort_qc.py

Test a new threshold on a benchmarking workspace with truth before changing the shipped value; record the evidence and change threshold_source from UNCALIBRATED_PROVISIONAL only with that evidence.

18. Add a workflow rule

  1. Add the rule to the right workflow/rules/lN_*.smk, with log: and benchmark: paths like its neighbours.
  2. Read threads and memory from config/registry/job_resources.yaml (add an entry).
  3. Add any new tool to a feature in pixi.toml and re-lock (section 20).
  4. Dry run on fixtures for every affected design; then integration tests.
pixi run pytest -q tests/unit/test_resource_plan.py
pixi run python scripts/verify.py --dry-run-only --output /absolute/path/new-preflight
pixi run pytest -q tests/integration

19. Add a downstream analysis

  1. Contract in config/registry/downstream_analyses.yaml (designs, scales, prerequisites, metadata).
  2. Module in src/pfvarx/downstream/ with an honest USES_COHORT_MATRIX; write a status_manifest.json with a terminal state.
  3. Parameters in config/parameters/layer5.yaml; tools in a pixi.toml feature; bootstrap.py and installation.py must install them for that analysis.
  4. Dashboard: tab, headline numbers and view block in reporting/views.js (inside daViews).
  5. Tests: a unit test for the method, an entry in the all-analyses integration test.
  6. Docs: analysis guide table, SOP Section 4 matrix (md + html), docs/sequencing.md eligibility, CHANGELOG.
pixi run pytest -q tests/unit/test_matrix_declarations.py tests/unit/test_dashboard_views.py tests/unit/test_install_by_final_output.py

23. Release procedure

  1. On a branch from develop: set __version__ in src/pfvarx/__init__.py; update every current-release reference: README.md, docs/README.html, docs/status.md, docs/configuration-guide.md+.html, SOP md+html (title, "finalized … " and Appendix D), the sample-analysis and benchmarking guides and this guide; rename the top CHANGELOG.md section to ## X.Y.Z (YYYY-MM-DD).
  2. Check: pixi run pytest -q tests/unit/test_version.py, then the full ladder (section 12).
  3. Pull request into develop; after it merges, a pull request from develop into main (section 24).
  4. Tag main and build the archive with scripts/package.py from that tag (never git archive: main holds the development material):
git fetch origin --tags
git tag -a v0.0.0 origin/main -m "PfVarX 0.0.0"
git push origin v0.0.0
git worktree add ../pfvarx-v0.0.0 v0.0.0 && cd ../pfvarx-v0.0.0
pixi run python scripts/package.py --output "$PWD/../dist"
cd ../dist && sha256sum -c pfvarx-0.0.0-source.zip.sha256
gh release create v0.0.0 --verify-tag --latest --title "PfVarX 0.0.0" --notes-file release-notes.md \
  pfvarx-0.0.0-source.zip pfvarx-0.0.0-source.zip.sha256
gh release download v0.0.0 -D /tmp/check && (cd /tmp/check && sha256sum -c pfvarx-0.0.0-source.zip.sha256)
pfvarx-0.0.0-source.zip: OK
A tag of the same name that already points elsewhere must be replaced deliberately: delete its GitHub release first, then git tag -d vX.Y.Z && git push origin :refs/tags/vX.Y.Z before creating it again. Published versions should normally never be re-used.

24. Bring develop to main

After a change is merged into develop and its tests pass there, bring main level with one pull request. Do not use --delete-branch here: it would delete develop.

git fetch origin
git diff --stat origin/main origin/develop       # only the tested change should be listed
gh pr create --base main --head develop --title "…" --body "Brings main level with develop (#NN)."
gh pr merge develop --merge
git fetch origin && git diff --quiet origin/main origin/develop && echo "main = develop"
main = develop

Never open a separate feature branch against main: a branch built from main while develop moves on conflicts with the next develop → main merge.
