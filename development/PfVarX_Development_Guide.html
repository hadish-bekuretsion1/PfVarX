PfVarX Development Guide

Everything needed to maintain, change, test and update PfVarX on your own computer: every tool, package and algorithm with its path and purpose; how to test parameters and choose the best; how to replace a tool that is slow or inaccurate; and every Git and GitHub command for this project.

Part A · Start

1. How development works

There are two kinds of folders. Keep them apart and most mistakes cannot happen.

Development copy

~/PfVarX is the Git clone of the repository. Permanent changes are made here, on a branch, then tested and merged through GitHub.

Test workspace

A folder such as ~/pfvarx-lab/exp-baseline holds one study's configuration, inputs and runs. Experiments happen here; nothing in it goes to GitHub.

Branches

main holds released code, develop collects finished changes, and each change gets its own branch, for example step/04-markdup-tool.

Every change follows the same path:

  1. Measure what you want to improve: speed, memory or accuracy of the current setting or tool (section 12).
  2. Try the alternative in a test workspace and compare it with an unchanged run on the same data (sections 9–13).
  3. Decide from the numbers. Record what you tried, the data and the result.
  4. Make it permanent on a branch in ~/PfVarX: code, tests and documentation together (sections 13–16).
  5. Release it: pull request into develop, CI, merge, then develop into main (section 19).

9. Experiment safely in a test workspace

Experiments change only a test workspace; the source in ~/PfVarX and on GitHub stays untouched. Make one baseline, run it unchanged, then copy it for every variant.

mkdir -p ~/pfvarx-lab
python3 ~/PfVarX/bootstrap.py --profile development --workspace ~/pfvarx-lab/exp-baseline
cd ~/pfvarx-lab/exp-baseline
# set the release label and final output in config/config.yaml (or use the GUI), then:
./pfvarx init
./pfvarx fixture --design wgs --depth 30          # synthetic test data, or add your own files
./pfvarx validate && ./pfvarx prepare && ./pfvarx pipeline --mode NEW

The workspace has its own copies of config/parameters/, config/registry/, src/ and workflow/. Edits there change only that workspace's runs. To make a variant:

cd ~/pfvarx-lab
rsync -a --exclude .pixi --exclude runs --exclude results exp-baseline/ exp-variant1/
cd exp-variant1                                   # edit, then ./pfvarx pipeline --mode NEW

The copy reuses the baseline's inputs and prepared reference. Leaving out .pixi saves 1–3 GB; Pixi recreates the environment from its cache on the first ./pfvarx command.

Which data? Synthetic data (./pfvarx fixture) shows whether a change works. To decide whether it is better, use reads with known answers: reference strains (3D7, Dd2…), replicate samples, mixtures of known proportion, or your own cohort.

10. Choose the best parameter value

To compare several values of one parameter, run the same data once per value and compare the results. Save the two scripts below in ~/pfvarx-lab/ once.

Run a grid of values: grid.sh

#!/usr/bin/env bash
# Usage: ./grid.sh LAYER PARAMETER "VALUE1 VALUE2 ..."
#   e.g. ./grid.sh layer1 fastp_length_required "30 50 70"
# Copies ~/pfvarx-lab/exp-baseline once per value, sets the parameter and runs it.
set -euo pipefail
LAYER=$1; KEY=$2; VALUES=$3; BASE=~/pfvarx-lab/exp-baseline
for v in $VALUES; do
  ws=~/pfvarx-lab/grid-$KEY-$v
  rm -rf "$ws"
  rsync -a --exclude .pixi --exclude runs --exclude results "$BASE/" "$ws/"
  python3 - "$ws/config/parameters/$LAYER.yaml" "$KEY" "$v" <<'PY'
import re, sys
path, key, value = sys.argv[1:]
text = open(path).read()
new, n = re.subn(rf"^(  {re.escape(key)}: \{{value: )[^,}}]+", rf"\g<1>{value}", text, flags=re.M)
if n != 1:
    sys.exit(f"{key} not found in {path}")
open(path, "w").write(new)
PY
  echo "== $KEY = $v"
  (cd "$ws" && ./pfvarx validate > /dev/null && ./pfvarx pipeline --mode NEW > run.json; tail -c 200 run.json)
done

Compare the runs: grid_summary.py

#!/usr/bin/env python3
"""Usage: python3 grid_summary.py ~/pfvarx-lab/exp-baseline ~/pfvarx-lab/grid-*
One row per workspace (its latest run): QC verdicts, read and depth metrics, variant
statuses and total step time, from runs/<RUN_ID>/results/report/dashboard_data.json."""
import json, statistics, sys
from collections import Counter
from pathlib import Path

def mean(values):
    values = [v for v in values if isinstance(v, (int, float))]
    return round(statistics.mean(values), 4) if values else None

print("\t".join(["workspace", "PASS", "WARNING", "FAIL", "reads_kept", "median_depth",
                 "callable", "duplicates", "variants", "PASS_calls", "low_conf", "step_time_s"]))
for ws in map(Path, sys.argv[1:]):
    reports = sorted(ws.glob("runs/*/results/report/dashboard_data.json"))
    if not reports:
        print(f"{ws.name}\t(no run)")
        continue
    d = json.loads(reports[-1].read_text())
    verdicts = Counter(s["qc_verdict"] for s in d["samples"])
    metric = lambda key: mean([s["metrics"].get(key) for s in d["samples"]])
    statuses = d.get("variant_summary", {}).get("statuses", {})
    wall = sum(m.get("wall_s") or 0 for m in d["resources"]["measured"])
    print("\t".join(str(x) for x in [ws.name, verdicts["PASS"], verdicts["WARNING"], verdicts["FAIL"],
        metric("reads_retained_fraction"), metric("median_depth_core"), metric("callable_fraction_core"),
        metric("duplicate_fraction"), d.get("variants_total"), statuses.get("PASS"),
        statuses.get("LOW_CONFIDENCE"), round(wall, 1)]))
cd ~/pfvarx-lab
chmod +x grid.sh
./grid.sh layer1 fastp_length_required "30 50 70"
python3 grid_summary.py exp-baseline grid-fastp_length_required-*  | column -t

How to choose

  • Prefer the value that keeps the most usable data (reads kept, callable fraction, PASS calls) without raising errors: more LOW_CONFIDENCE calls, more QC WARNINGs, or calls that disagree with known answers.
  • With a truth set, decide on accuracy first (section 12: precision and recall), then on speed.
  • Change one parameter at a time; test interactions only after single effects are clear.
  • Record the grid, the data and the decision, then make the chosen value the default (section 14) with source EMPIRICALLY_CALIBRATED and the evidence in docs/thresholds.md.

12. Measure speed and accuracy

Speed and memory

Every step of every run is measured by Snakemake:

RUN=runs/<RUN_ID>
# seconds (s) and peak memory in MB (max_rss) for every step and sample
for f in $RUN/benchmarks/*/*.tsv; do printf "%-45s " "${f#$RUN/benchmarks/}"; tail -1 "$f" | cut -f1,3; done | sort -k2 -n -r | head -20
# the same, summed per step, is in the report: Resources section

Compare the same step between a baseline and a variant run on the same data and the same computer. Run each at least twice; the first run may include file-cache effects.

Accuracy

  • Alignment and duplicates: mapped and properly-paired fractions, duplicate fraction, depth and callable fraction (grid_summary.py, the QC section of the report).
  • Variant calls against a truth set: the benchmarking workflow compares calls with truth VCFs (RTG Tools vcfeval) and reports precision, recall and WSAF agreement. Use a separate benchmark workspace:
python3 ~/PfVarX/bootstrap.py --profile benchmark --rtg --workspace ~/pfvarx-lab/bench
cd ~/pfvarx-lab/bench
# put truth.json, confident_regions.bed and <SAMPLE>.truth.vcf in inputs/truth/ (see docs/benchmarking/README.md)
./pfvarx benchmark-partition                       # lock development / held-out samples, once
./pfvarx pipeline --mode NEW
./pfvarx benchmark-evaluate                        # precision, recall, WSAF on the development set
./pfvarx benchmark-resources                       # measured resource profile
Use the held-out set once. Tune and compare on the development samples. Evaluate the final choice on the held-out samples a single time; repeating it turns the held-out set into training data.

13. Replace or upgrade a tool

Replace a tool when measurements show it is slow, uses too much memory, gives worse results, or is no longer maintained. Worked example: replacing Picard MarkDuplicates with samtools markdup for WGS duplicate marking.

  1. Measure the current tool on a baseline run: time and memory of the markdup step (section 12) and the duplicate fraction per sample.
  2. Try the new tool by hand on one sample in a test workspace, without changing the pipeline: 
    cd ~/pfvarx-lab/exp-baseline
RUN=runs/<RUN_ID>; IN=$RUN/results/work/merged/PF001.bam      # needs retention: intermediates: keep
time ( ./pfvarx tool samtools sort -n -o /tmp/qn.bam $IN &&
       ./pfvarx tool samtools fixmate -m /tmp/qn.bam /tmp/fm.bam &&
       ./pfvarx tool samtools sort -o /tmp/pos.bam /tmp/fm.bam &&
       ./pfvarx tool samtools markdup -s -f /tmp/markdup.txt /tmp/pos.bam /tmp/PF001.md.bam )
cat /tmp/markdup.txt                                # duplicate counts
grep -A2 "^LIBRARY" $RUN/results/qc/samples/PF001/PF001.markdup.txt   # Picard's, to compare
  3. Decide from time, memory and duplicate fractions on several samples, then create a branch: 
    cd ~/PfVarX && git checkout develop && git pull && git checkout -b step/04-markdup-tool
  4. Add the package if it is new. Put it under the right feature in pixi.toml (samtools is already in pipeline), then lock and install: 
    pixi lock && pixi install --locked && git diff --stat pixi.lock
  5. Change the rule. Edit the command of rule mark_duplicates in workflow/rules/l1_align.smk. Keep the same output files (alignments/<sample>.bam and the metrics file): later steps depend on them. To compare both tools, choose the tool with a new parameter instead, for example layer1.markdup_tool: {value: picard, source: FRAMEWORK_POLICY}, read as P["layer1.markdup_tool"].
  6. Keep the QC metrics working. src/pfvarx/quality/metrics.py parses each tool's report into the metric names the QC gates use (picard_duplicates() produces duplicate_fraction). Add a parser for the new tool's report that produces the same names, and use it in workflow/scripts/l1_gate.py.
  7. Update the bookkeeping for a new tool or package:
    • threads and memory of the rule → the job class in src/pfvarx/planning/plan.py (tests/unit/test_resource_plan.py checks they agree);
    • version recording → SCIENTIFIC_PACKAGES in src/pfvarx/provenance/snapshot.py;
    • the tools list in the GUI → TOOLS in src/pfvarx/installation.py;
    • which installation needs it → scripts/check_installs.py, and for a new feature environment_for() in bootstrap.py and the environments in pixi.toml.
  8. Test up the ladder (section 15): the one step, a fixture run, the comparison with the baseline, then the full suite and check_installs.py.
  9. Document (section 16) and release (section 19).
